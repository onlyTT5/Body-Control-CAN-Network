# 演示与面试说明

## 1. 60 秒项目介绍

这是一个双 STM32F103 的车身控制 CAN 网络。节点 A 负责人机交互、灯光命令、OLED 诊断、DTC 和 SPI Flash 持久化；节点 B 负责灯光执行、超声波测距、泊车蜂鸣器和健康监测。两个节点通过 500 kbit/s CAN 通信。我重点实现了非阻塞任务、命令序号与状态闭环、五点中值滤波、CAN 掉线和 bus-off 恢复、看门狗复位识别，以及带确认/恢复计数的 DTC 和冻结帧。项目最终通过 CAN 分析仪做了故障注入和完整回归。

## 2. 推荐演示顺序

1. 展示两节点、CAN 收发器、OLED、超声波和编码器的连接。
2. 打开 CAN 分析仪，指出 `0x101`、`0x111`、`0x114` 的周期。
3. 操作灯光按键，展示 `0x100` 命令、`0x102` 回传和实际 LED。
4. 移动目标物，展示距离报文和四级蜂鸣器。
5. 使用 EC11 浏览 DTC 摘要、明细和冻结帧。
6. 断开节点 B，展示离线 DTC；恢复后展示 active 清除但 history 保留。
7. 用 `0x115` 查询明细并解释 `0x116/0x117/0x118`。

## 3. 设计亮点怎么讲

### 为什么不用阻塞延时？

蜂鸣器、超声波、CAN 心跳、OLED 和输入扫描需要同时运行。若用 `HAL_Delay()` 等待回波或鸣叫节拍，主循环会停止处理其他任务。项目使用 `HAL_GetTick()`、定时器计数和状态机推进，每次循环只做短操作。

### 中值滤波是不是求平均？

不是。五点中值滤波保存最近 5 个有效距离，排序后取中间第 3 个。它能剔除单个过大或过小的跳变；平均值会被离群值拉偏。代价是需要积累样本，并带来少量响应延迟。

### 为什么报文里要有序号？

序号用于把命令和应答配对，并发现丢帧、重复帧或远端复位。仅传一个开关位无法判断收到的是本次命令还是旧状态。

### 为什么 DTC 需要确认和恢复计数？

瞬时噪声不应该立即变成故障，刚恢复的一帧也不应该立即清除 active。失败/通过计数相当于时间去抖，使状态更稳定。bus-off 风险更高，因此可立即确认。

### `ACTIVE:00 HISTORY:02` 是否矛盾？

不矛盾。它表示当前没有故障仍在发生，但有两个故障曾经被确认并存入历史。明细页的 `H:1` 表示该条有历史，`C:00002` 表示累计确认 2 次，不是总故障数。

### 为什么看门狗最后初始化？

IWDG 一旦启动通常无法由软件关闭。先完成时钟、SysTick、CAN、测距和应用状态初始化，再启动看门狗，可以避免初始化阶段耗时或依赖未就绪资源而反复复位。运行阶段只在关键任务正常推进时喂狗。

### CAN bus-off 如何恢复？

硬件自动 bus-off 管理负责满足总线恢复条件后的重新接入，软件负责记录错误状态、暂停不安全假设、保留 DTC，并在心跳恢复后重新同步应用状态。

### Flash 如何避免覆盖业务数据？

DTC、事件日志和自检分别使用固定独立扇区。事件日志采用固定长度记录并带魔数、版本和校验/验证流程，写满后按当前策略擦除日志扇区重新记录。量产方案还会进一步考虑磨损均衡、掉电原子性和冗余。

## 4. HAL 与标准库并存的解释

节点 A 使用 CubeMX/HAL，便于维护多外设配置并自动生成初始化代码；节点 B 使用标准外设库，保留了寄存器层面更直接的工程结构。协议和应用层不依赖某个库的 API，通过各自 BSP 隔离差异。

## 5. 项目边界与可继续优化的方向

回答局限时可以明确说明：

- 当前是教学台架，不是通过 ISO 26262、EMC 和环境验证的量产 ECU。
- CAN 协议为项目自定义，尚未采用 CANopen、UDS 或 AUTOSAR 通信栈。
- Flash 日志是简化的循环/重建策略，可继续加入双区提交、CRC 和磨损均衡。
- 调度器是裸机协作式结构，节点和任务继续增加时可评估 RTOS。
- 可增加单元测试、硬件在环自动化以及 CAN 报文数据库（DBC）。

## 6. 演示前准备

- 编译并下载已通过回归的固件，不临时修改测试宏。
- 提前确认 CAN 分析仪为 500 kbit/s、标准帧、正确采样点。
- 准备一个平整目标物和可重复的 20/50/100 cm 距离标记。
- 清楚解释每个 DTC 的制造和恢复条件，不在演示现场短接供电或总线。
- 保留一份 [CAN 协议表](can-protocol.md) 和 [回归测试表](testing.md) 便于快速定位。
